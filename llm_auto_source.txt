FOUNDATA: ADDING A NEW SOURCE (instructions for an LLM agent)
================================================================

Goal: turn a raw travel / time-use survey into (attributes, trips) polars
DataFrames that match configs/core/template.yaml, then register the source in
the pipeline. Raw formats vary (CSV, DBF, SPSS .sav, Nesstar, Excel, one
table or many), so investigate the data first and don't assume a layout.

RUNNING THINGS
- Tests: `uv run pytest` (pytest is in the dev extra). Lint: `uv run ruff check foundata/`.
- Validate configs: `uv run foundata validate-config <src>`. WARNs for
  intermediate columns are expected; ERRORs mean a mapped value isn't in the
  template's set.
- Run one source: `uv run foundata run <src> ~/Data/foundata/<SRC> -o <scratch>/out`
- Template smoke run: `uv run foundata batch data_dir_template -o <scratch>/out`
  This runs EVERY source by default, so a new source must have template data
  or this run breaks.
- Raw data lives under ~/Data/foundata/<Folder>/. Use the user's folder name
  everywhere: the data_root subdirectory in run.py, the DATA_ROOT paths in
  both generators, and data_dir_template/<Folder>/. If these drift apart
  (e.g. after the user renames the folder), the template run breaks.
- Regenerate one source only: `uv run python scripts/build_data_dir_template.py <src>`
  takes source names; generate_fixtures.py runs everything, so call its
  function directly: `cd scripts && uv run python -c "import generate_fixtures as g; g.generate_<src>()"`.
- Put exploration scripts in the scratchpad, in their own folder. Never name a
  scratch file after a stdlib module: an `inspect.py` in the scratchpad broke
  the polars import.

REPO MAP
- configs/core/template.yaml: the output schema. Lists the fields, dtypes,
  allowed value sets, and whether unknown/null is allowed. Read it first.
- configs/<src>/{hh,person,trip}_dictionary.yaml: column_mappings (raw ->
  template or intermediate name) plus per-field value maps. Keys named after
  a template field (sex, mode, dact, employment, ...) are checked by the
  validator, so use those names where possible. Put other source parameters
  in the YAML too (exchange rate, thresholds, circuity, ...) rather than
  hard-coding them.
  - column_mappings can nest one dict per raw table (TVIAJE: {...},
    TTRANSPORTE: {...} in mexico); the validator flattens them.
  - Multi-year sources nest a `default:` key plus per-year keys; read them
    with utils.config_for_year.
  - Waves with very different layouts (ktdb 2010/2016/2021) still share
    one nested dictionary: give a key a per-year value for every year (no
    `default` needed), or `default: {}` / `default: null` when only some
    years use it. The loader then keeps one load_<year> path per wave.
  - The validator accepts `ft-employed`/`pt-employed` for employment, since
    utils.split_employment_type turns them into employed + employed_type.
- foundata/<src>.py: the loader. Exposes `load(...)` or `load_years(...)` and
  returns (attributes, trips).
- foundata/run.py: add the import, add a `_load_<src>(source_dir)` function
  (load the configs with `_configs`, call the loader) and register it in the
  `SOURCES` dict, which also makes it a `foundata run <src>` CLI choice.
  load_source then applies process_source, which does the shared cleaning: avg_speed,
  employment split, child employment, time/activity filters, missing columns,
  type fixes, weight normalisation.
- foundata/utils.py: table_joiner, config_for_year, sample_to_euro
  (samples within income brackets), assign_retired, get_config_path, ...
- foundata/fix.py: day_wrap (call it after computing tst/tet), missing_columns,
  fix_types.
- foundata/cli.py: OPEN_SOURCES drives --open and the published
  open_foundata.zip. Ask the user before adding to it.
- scripts/scaffold_source.py <src>: stub configs and loader. Optional; copying
  the closest existing loader is often faster.
- scripts/generate_fixtures.py -> tests/fixtures/<src>/ (~50 households).
- scripts/build_data_dir_template.py -> data_dir_template/<Folder>/ (a handful
  of households). Register the generator in GENERATORS. Licensing decides the
  treatment: open data is sampled unmodified; restricted data gets fresh
  synthetic ids and shuffled attribute columns, with trip rows kept intact.
- Format helpers already written: scripts/dbf_writer.py (byte-exact DBF
  subset; sample_brazil for one flat table, sample_mexico for linked tables
  sampled hh -> persons -> trips -> stages), scripts/nesstar_writer.py + ddi_writer.py (Nesstar),
  brazil.read_dbf (numpy DBF reader).
- tests/test_<src>.py: load test on the fixtures (env var
  FOUNDATA_<SRC>_DATA overrides the path), plus unit tests on small
  hand-built inputs for each tricky transform.
- README.md: add a row to the Data Sources table (and remove it from
  "In progress/todo"), and add the name to the "Available sources" list.
- Example loaders: brazil (one flat table with hh, family, person and trip
  levels), ktdb (no hh id, zone lookups, staged modes), qhts/vista (separate
  hh/person/trip CSVs over several years), india (time-use diary), nts/ltds
  (stages), mexico (linked DBF tables, weekday + Saturday diary per person,
  distance from stage durations x mode speed), nts (several diary days per
  person split into person-days), argentina (several surveys in one source,
  SPSS .sav via pyreadstat, per-survey column_mappings and value maps).

OUTPUT CONTRACT (check template.yaml for the full list)
- attributes: one row per person. pid and hid are strings prefixed with the
  source name (e.g. "brazil" + raw id). Include people who made no trips: they
  get a home-all-day plan downstream.
  - Set programmatically: source, country (existing codes are mixed: "kr",
    "nl", "uk", "br", "mx", "usa", "aus", "ind"), year, month, and day (lowercase
    weekday name).
  - hh_income: annual EUR as Int32. Convert currency and period (monthly x12)
    and record the rate in the config. Use null when unknown, never 0
    (0 means a real zero income).
  - Columns the source lacks: fill categoricals with "unknown". Use "void"
    where the field doesn't apply, e.g. occupation for people not employed.
  - weight: Float32.
  - access_egress_distance: optional; km of walking or other access stages on
    transit trips, averaged per person.
- trips: pid, seq (Int8, 0-indexed), ozone/dzone (urban|suburban|rural|unknown),
  oact/dact, mode (walk|bike|car|bus|rail|other|unknown), tst/tet (Int, minutes
  since midnight, may go above 1440 after day_wrap), distance (Float32, km).
  Drop helper columns before returning.
- Activities: home, work, education, shop, leisure, visit, escort, other.
  There is no "medical" in the template, so map medical to other. Meals ->
  shop. Motorbike -> car. Taxi / ride-hail -> car.
- oact of trip n should equal dact of trip n-1;
  filter.activity_consistency drops plans where it doesn't.
- hh_location (attributes) and ocode/dcode (trips) are location keys
  written by location.add / add_trip_ends (see LOCATIONS below), which the
  runner turns into ids; activities' location is derived from them.

LOCATIONS (homes and trip ends; see the foundata/location.py docstring)
- The config only lists levels and their lookup files. In hh_dictionary.yaml
  under home_location, list the levels finest first, each with its lookup
  in configs/<source>/geo/:
      home_location:
        2023:
          - level: pc4
            geo: pc4.parquet
          - level: gemeente
            geo: gemeente_2023.parquet
        default:
          - level: gemeente
            geo: gemeente_2024.parquet
  Blocks are keyed by survey year (or survey name), with default for the
  rest; a plain list applies to every survey. A point level is
  "- level: point" with "scale_m: <assumed uncertainty>" and no geo.
- All the logic is in the loader. Before calling location.add, write one
  clean code column per level, <role>_<level> (home_pc4, home_gemeente):
  a string in the lookup's code format, null where unknown or invalid.
  Use location.clean(col, width=, valid=, missing=) to strip, zero-pad and
  validate, and location.mapped(col, source, "<file>.csv") to map survey
  numbering to standard codes with a from,to csv in configs/<source>/.
  For a point, write <role>_lon/<role>_lat in WGS84 (location.wgs84
  projects x, y from the survey's CRS). Then call
  location.add(hhs, source=..., key=<year or survey>) once (its
  LocationFinder reads the declaration from the config). It writes hh_location: the key <source>/<geo>/<code> of
  the first level whose code is in its lookup (a code the lookup lacks
  falls through; the last level keeps it), or <source>/point/<lon>,<lat>,
  and drops the code columns it read. The runner turns keys into
  location ids (LocationFinder.index). Never write hh_location yourself.
- Trip ends: declare trip_location the same way in trip_dictionary.yaml,
  once for both ends. Write origin_<level> and destination_<level> code
  columns (origin_lon... for points) while the raw zone codes are still
  there (before they become urbanity) and call
  location.add_trip_ends(trips, source=..., key=...), which writes
  the ocode and dcode keys. Keep ocode and dcode in the trips you return.
- Levels: a level is a kind of unit (gemeente, sa1, tract) and gives the
  precision class (location.LEVEL_PRECISION; add new ones there). The geo
  file gives the vintage: name it <level>_<year> where codes are
  renumbered or redrawn between rounds (gemeente_2012.parquet). Use
  standard codes (ONS, FIPS, ABS, CBS, INDEC, KOSTAT, NSO...) where the
  survey allows.
- Lookups: each geo file is a GeoParquet lookup, built by
  scripts/build_location_lookups.py: add the boundary file to DATASETS and
  a builder for the source (BUILDERS), which writes configs/<source>/geo/
  <name>.parquet. The builder builds every geo file the source's
  declarations name (location.geo_files), so a new survey year means
  adding its block and rebuilding. Put name aliases in
  a yaml next to the lookup, not in the script. If the unit has no
  published boundary, use the containing unit (geom_source parent) or flag
  a provisional area as estimated; never leave it silently missing.
  scripts/build_location_lookup.py builds one lookup from a local file.
- Check: tests/test_location.py validates every declaration and lookup
  (and that each geo file exists); tests/test_locations_batch.py runs
  data_dir_template and checks codes have their lookup's format. Run
  foundata location-summary <batch output> for the README location table,
  and update both README location tables.

WORKFLOW
0. If the user asks whether a dataset is usable, or it's a new candidate,
   follow llm_verify_source.txt first and bring back a verdict. Its checks
   cover most of step 1.
1. Inspect the raw data before writing any code:
   - list the files and find the codebook / layout doc (often xlsx or docx,
     possibly not in English);
   - read the schema and row counts;
   - work out the entity hierarchy and the id columns, and check them:
     hh-level fields constant within hh, person count == stated hh size,
     trips per person == stated trip count;
   - check how people with no trips are represented;
   - check how missing values are encoded;
   - check time formats, distance units (metres? miles? straight-line?), the
     date vs travel-day relationship, and how weights are named.
   Report findings and ask before building if anything is ambiguous.
2. Write the configs from the codebook, putting the original label in a
   comment next to each code. Validate.
3. Write the loader and smoke-test it on the real data. Print value_counts
   for every categorical and describe() for the numerics. Look for unexpected
   unknowns, nulls, unit errors, and odd weekday/month distributions.
4. Run the pipeline for the source alone. Check the attribute availability
   table and how many plans each filter drops: >5% dropped usually means a
   mapping or timing bug.
5. Add fixture and template generators, run them, then add tests and run the
   full suite and the data_dir_template run.
6. Declare home (and trip end) locations and build their lookups (see
   LOCATIONS). Update run.py and the README. Summarise the judgement calls
   to the user.
   Do not commit unless asked.

GOTCHAS SEEN SO FAR
- Missing values may be encoded as sentinels: "*"/"**" padding (SP DBF),
  "Missing/Refused", 99/98/97, blanks, negative codes. A pandas to_numeric
  with coerce hides these; polars strict casts expose them. Prefer that.
- replace_strict with integer YAML keys needs the column cast to int first.
  Use default="unknown" for unmapped codes, or polars raises.
- Times: may be split into hour and minute columns, offset from a non-midnight
  anchor (QHTS counts from 04:00), given as HHMM integers, or given as
  durations. Always call fix.day_wrap.
- Travel day vs interview date: they can differ (SP interviews happen the
  day after travel). Derive day/month/year from the travel day.
- Intermediate levels: a household can contain several families (SP).
  Aggregate income and vehicles to the household and say how you did it.
  Some sources have no household id at all (KTDB): set hid = pid.
- Income is often imputed by the survey, or recorded per person rather than
  per household. Flag imputation shares to the user and make inclusion
  configurable.
- Zone urbanity: there is rarely a direct field. Options: a lookup CSV in
  configs/<src>/, the zone name suffix (KTDB), or density = weighted residents
  / zone area (SP, area taken from the shapefile's .dbf, so no geometry
  library is needed). Non-residential zones end up as unknown; that's fine.
- Distances given as straight-line are multiplied by a circuity of 1.3. If
  there is no distance, use zone-centroid distances (KTDB) or
  duration x mode speed.
- Escort purpose may be a separate flag rather than a purpose code (SP
  SERVIR_O/SERVIR_D).
- Persons without trips: keep them in attributes. The "Missing N% of 'pid'
  keys in 'trips'" warning is expected.
- The many "ERROR: Column X has dtype ..." lines during run are reported
  before fix_types runs and are present for existing sources too. Still cast
  your own columns to the template dtypes.
- The template-run sample is tiny, so derived statistics (e.g. zone density)
  differ from the real data. Tests should check structure, not values that
  depend on the sample.
- Don't add heavy dependencies for one file format if a ~40-line reader will
  do (DBF). pyproject's `scripts` dependency group (geopandas) is available
  to scripts only, not to loaders.
- The codebook is often not in the user's download. Look on the publisher's
  page for an open-data / "datos abiertos" bundle: INEGI's CSV zip carried
  diccionario_de_datos/ and catalogos/ for every table even though the user
  only had the DBFs. Download into its own scratch folder.
- Publisher pages are often JS-rendered (WebFetch returns only the title).
  curl the HTML and grep for .zip/.pdf/.xlsx links instead. Don't probe
  guessed URLs with HEAD: some servers answer 200 for everything.
- Several diaries per person (weekday + Saturday in mexico, 7 days in nts):
  ask whether to keep all of them. If yes, make one attributes row per
  person-day, with pid = raw id + diary suffix and the same hid, and set day
  per diary. A day that's only known as "a Tue-Thu" is day "unknown".
- Persons not asked the travel questions (mexico: under 6, P4_2 blank) are
  different from persons who reported no trips. Drop them from attributes
  rather than giving them a home-all-day plan, but still count them in
  hh_size.
- Stage tables (one row per mode used): pick the trip mode by a priority list
  in the config (rail > bus > car > other > bike > walk) rather than by
  longest stage, otherwise a long walk to the metro makes it a walk trip.
  When distance comes from stage duration x speed, share an unknown stage's
  duration from the trip time the known stages don't cover. Stage times
  that include waiting need lower, door-to-door transit speeds.
- Zone urbanity from a locality-size field (mexico TLOC): map it to hh_zone
  directly, and classify trip zones by the weighted modal hh_zone of the
  households living in each zone.
- Run the source on its own (-s <src>) as well as with the rest: the
  plotting and summary steps can fail when an attribute is null for every
  row (the hh_income heatmap did until it was guarded).
- polars: Expr.sum() has no min_count, so for a null-if-any-null sum use
  pl.when(col.is_not_null().all()).then(col.sum()). Passing a Series to
  is_in is deprecated; pass series.implode().
- SPSS .sav (pyreadstat): `usecols` silently skips variable names it can't
  decode, so check the returned columns. Names or strings in the wrong
  encoding: try encoding="latin1", else transliterate the names in a copy
  (argentina.ascii_long_names).
- A filter like ~(age < 3) drops rows with null age; add fill_null(False).
- Dutch sources (odin, ovin, mon) share foundata/nl_income.py and
  configs/nl/nl_income.yaml: income is converted to gross household income
  by rank against CBS decile boundaries, and open top bands are sampled from
  a Pareto tail capped at a shared max_income. Use them for any new NL
  source rather than a fixed upper bound.
- If a test fails after an intended code change, ask the user or fix the
  test. Don't revert the change on the assumption it was a regression.
